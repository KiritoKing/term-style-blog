## 上下文

站点为 Astro 博客（Astro 5 + React + TypeScript），整体 UI 以“像素风 + 命令行 UI”作为视觉主题，文章页为静态生成。目标是在不引入自建后端与数据库的前提下，给文章详情页增加评论与反应能力，并确保评论区视觉风格与站点一致、加载范围可控。

参考 UI（`reference/ref-template-new-2`）提供了整体布局、字体模式（pixel/system）、扫描线/CRT 效果、面板边框与按钮风格。但该参考目录中未直接包含评论区组件实现；因此实现上以站点现有布局与样式为基准，提取参考 UI 的可复用视觉语言（边框、底纹、字号、强调色、按钮态）应用到 giscus 自定义主题中。

约束：
- 优先 Astro 静态渲染；React 仅用于必要交互区域。
- 最小化客户端 JS；评论区只在文章详情页加载。
- giscus 通过第三方脚本加载并渲染在 iframe 内，样式需要通过 giscus 主题机制下发。

## 目标 / 非目标

**目标：**
- 在文章详情页嵌入 giscus 评论区，支持评论与反应（reactions）。
- 评论区外观与站点“像素风 + 命令行 UI”一致，包括：细线分隔、浅灰底纹、等宽字体、低饱和强调色与按钮交互态。
- 支持与站点主题切换的策略（至少支持浅色；如站点已有深色模式则提供对应映射）。
- 提供可维护的配置入口，避免把大量 data-* 配置散落在页面模板中。

**非目标：**
- 不实现自建评论后端、账号体系或数据库。
- 不实现对 giscus 业务逻辑的二次开发（仅通过公开配置与主题能力实现）。
- 不在非文章页展示评论区（如首页/列表页/分类页）。

## 决策

- 仅在文章页注入 giscus
  - 方案 A：在全局布局注入并通过页面条件隐藏
  - 方案 B：仅在文章详情页组件化注入
  - 选择 B：降低无关页面的脚本开销，减少潜在安全面，符合最小化客户端 JS 的约束。

- 使用 giscus 的自定义主题（data-theme 指向 CSS URL）
  - 方案 A：使用内置主题（light/dark 等）
  - 方案 B：自定义主题 CSS，复刻站点终端风格
  - 选择 B：确保与现有 UI 高一致性，并能持续迭代细节（边框、底纹、字体、按钮态）。

- 主题切换策略
  - 方案 A：固定一个主题（仅浅色）
  - 方案 B：根据站点主题向 iframe 发送配置切换（postMessage）或重载脚本
  - 初始选择 A：先落地浅色终端主题，确保最小可用；若站点已有稳定暗色模式再补充 B。

- 映射策略使用 pathname
  - 方案 A：按 URL（window.location.href）
  - 方案 B：按 pathname
  - 方案 C：按 title
  - 选择 B：与 Astro 路由结构稳定一致，避免标题变更导致 discussion 迁移；在需要时开启严格匹配避免误关联。

- 安全与来源限制（可选）
  - 通过仓库根目录 giscus.json 配置 origins/originsRegex 限制可加载来源，降低被第三方站点“复用”讨论区的风险。

## 风险 / 权衡

- [外部 CSS 安全风险] → 主题 CSS 必须托管在可信域名并由站点构建产出，避免第三方可篡改。
- [iframe 样式可控性有限] → 通过 giscus 主题机制覆盖主要 UI；对少数无法覆盖的细节接受差异或通过容器布局兜底。
- [主题切换复杂度] → 初期以单主题落地；若需要深色模式，再引入与站点主题同步的机制。
- [映射误匹配] → 在存在相似标题/路径等极端情况时，启用 data-strict 并按需迁移历史 discussions。
