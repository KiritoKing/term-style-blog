# Design

## Compatibility boundary

Schema version 1 hashes the JSON text of a globally path-sorted array whose object insertion order is `slug`, `status`, `title`, `path`, `bytes`, `sha256`. JSON object order is therefore part of the already-deployed hash contract even though it is not represented by `exactKeys`. The consumer will construct a new object in that explicit order after it independently validates file bytes and frontmatter.

The producer remains unchanged. Existing immutable manifest bytes and `source_tree_hash` values must validate after the consumer repair.

## Discovery order

Recursive directory traversal is deterministic per directory but is not a global path sort. The consumer will sort the final discovered file list by normalized relative path. A golden fixture containing both `a.md` and `a/child.md` makes this distinction observable.

## Golden provenance

The fixture is generated by running the checked-in Deno exporter against synthetic Markdown only. It contains both public statuses, Unicode metadata and paths, nested paths, and the `a.md`/`a/child.md` ordering edge. A provenance file records the exporter schema, tested runtime and SHA-256 of the exporter source files used. Tests read exporter-produced manifest bytes and derive expected hashes from those bytes rather than rebuilding the producer expectation in Node.

Real publication content is downloaded read-only only into the owned temporary directory for one validation command and is never copied into the repository.
